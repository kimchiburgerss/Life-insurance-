# Deployment guide

How to put Heir Finder on the internet for real use. The worked example is
**Render** (a `render.yaml` Blueprint is in the repo); the last section covers
other hosts. Read [SECURITY.md](SECURITY.md) and the pre-launch checklist in
[OPERATIONS.md](OPERATIONS.md#pre-launch-checklist) before switching off mock mode.

> Field names and plan names below follow Render's documentation as of this
> writing (render.com/docs/blueprint-spec, render.com/docs/postgresql-backups).
> Render changes plans from time to time — check them when you set up.

## What you are deploying

| Piece | What it is |
|-------|-----------|
| Web service | One Docker container built from `Dockerfile` (final stage `runner`): the Next.js server **and** the background-job worker (pg-boss) in one process. Run **exactly one instance** — two would both run the nightly jobs. To scale out later, set `RUN_JOBS=false` on the extra instances. |
| Database | Managed PostgreSQL 17. Everything lives here: cases, encrypted contact details, encrypted documents, the audit log, the job queue. |
| Migrations | `sh /app/migrate.sh` inside the image (Prisma `migrate deploy`: forward-only, never resets data). Run before each release starts. |
| Rules | The Nevada jurisdiction rules shipped with each version are added on startup. Existing rules — and your verification of them — are never changed. |
| Health check | `GET /api/health` (checks the database; returns no data). |

## 1. Before you start

- A Render account (enable two-factor authentication on it, and on GitHub).
- The repository on GitHub, connected to Render.
- A domain name (e.g. `app.yourfirm.com`) — letters and emails link to it, so pick it once.
- Generate three secrets **on your own computer** and store them in your password manager:

  ```bash
  openssl rand -base64 32   # PII_ENCRYPTION_KEY
  openssl rand -base64 32   # PII_HMAC_KEY (a different value)
  ```

  Also keep a **paper or offline copy** of both PII keys, separate from database
  backups. Without `PII_ENCRYPTION_KEY`, encrypted contact details and documents
  can never be read again. (`BETTER_AUTH_SECRET` is generated by Render.)

## 2. Create the services from the Blueprint

1. Render dashboard → **New** → **Blueprint** → choose this repository. Render
   reads `render.yaml` and proposes a web service `heir-finder` and a database
   `heir-finder-db`.
2. Fill in the values it asks for (`sync: false` in the file):
   - `BETTER_AUTH_URL` and `PUBLIC_APP_URL`: `https://app.yourfirm.com` (your domain, no trailing slash).
   - `PII_ENCRYPTION_KEY`, `PII_HMAC_KEY`: the values you generated.
   - Leave the vendor keys (`ANTHROPIC_API_KEY`, `LOB_*`, `SMTP_*`, `DROPBOX_SIGN_API_KEY`, `STRIPE_*`) empty for now. `MOCK_MODE` stays `"true"`.
3. Database plan: choose a **paid** plan. Render's point-in-time recovery
   (restore to any moment in the retention window) is only on paid databases —
   3 days on a Hobby workspace, 7 days on Pro and above, per Render's docs.
   `ipAllowList: []` keeps the database off the public internet.
4. **Apply**. The first build takes a few minutes. Before the server starts,
   the pre-deploy command applies every migration; on start the app adds the
   jurisdiction rules. The service turns "Live" once `/api/health` answers.

## 3. Your domain and HTTPS

Web service → **Settings → Custom Domains** → add `app.yourfirm.com` and create
the DNS record Render shows. Render issues and renews the TLS certificate. Once
it is active, open `https://app.yourfirm.com/login`. The app sends HSTS, so only
use the HTTPS address from then on.

## 4. Create your owner account

Public sign-up is disabled. Create the first OWNER from your computer, against
the production database:

1. Database → **Access Control**: temporarily add your current IP address.
2. Copy the database's **External Database URL**.
3. In your local checkout:

   ```bash
   DATABASE_URL="<external URL>" npm run user:create -- --email you@yourfirm.com --name "Your Name" --role OWNER
   ```

   (You are prompted for a password of at least 12 characters. This command
   needs only the database URL — no other production secret leaves Render.)
4. Remove your IP from Access Control again.
5. Sign in at `/login`; you are sent to `/setup-2fa` to enrol your authenticator app.

Never run `npm run db:seed` with demo data against production; it refuses when
`NODE_ENV=production` or `SEED_DEMO=false`.

## 5. Connect the vendors (still in mock mode)

Add each key in **Environment** and save (Render redeploys):

| Vendor | Variables | Webhook URL to register at the vendor |
|--------|-----------|--------------------------------------|
| Anthropic (AI) | `ANTHROPIC_API_KEY` | — |
| Lob (letters) | `LOB_API_KEY` (start with a `test_` key), `LOB_WEBHOOK_SECRET` | `https://app.yourfirm.com/api/webhooks/lob` |
| Your mailbox (email) | `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASS` (an app password) | — |
| Dropbox Sign | `DROPBOX_SIGN_API_KEY` (keep `DROPBOX_SIGN_TEST_MODE=true` until your attorney's agreement is switched on) | account callback: `https://app.yourfirm.com/api/webhooks/esign` |
| Stripe | `STRIPE_SECRET_KEY` (a **restricted key**: write access to Customers, Invoices and Invoice items only), `STRIPE_WEBHOOK_SECRET` | `https://app.yourfirm.com/api/webhooks/stripe` — events `invoice.paid`, `invoice.voided`, `invoice.marked_uncollectible`, `invoice.payment_failed` |

**Settings** in the app shows whether each service is configured (never the values).
Switch `MOCK_MODE` to `"false"` only after the [pre-launch checklist](OPERATIONS.md#pre-launch-checklist).

## 6. Releasing updates

- Merge to the branch Render deploys from. Render builds the image, runs
  `sh /app/migrate.sh`, starts the new container, waits for `/api/health`, then
  switches traffic. If the health check fails, the old version keeps running.
- Migrations only move forward. Never edit a migration that has run in
  production; add a new one.
- **Rolling back code**: Render → service → **Events** → roll back to the
  previous deploy. A rollback doesn't undo migrations; all migrations so far
  only add columns, tables and triggers, so older code keeps working.
- **Rolling back data** (a bad migration or a mistaken bulk action): restore the
  database with point-in-time recovery to a new database, check it, then point
  `DATABASE_URL` at it (see OPERATIONS.md → Restoring from a backup).

## 7. After going live

- Set up the nightly off-site `pg_dump` and the quarterly restore drill (OPERATIONS.md → Backups).
- Add an external uptime check on `https://app.yourfirm.com/api/health` (e.g. a free uptime monitor) that emails you.
- Turn on Render's deploy-failure notifications.

## Other hosts

The image is host-neutral. Whatever the host:

1. Build the final stage of `Dockerfile` (`docker build -t heir-finder .`).
2. Provide PostgreSQL 17 and the same environment variables as above.
3. Run `sh /app/migrate.sh` from the image **before** each new version starts
   (Fly.io: `release_command = "sh /app/migrate.sh"` in `fly.toml`; Railway: a
   pre-deploy command; Docker Compose: `docker compose run --rm app sh /app/migrate.sh`).
4. Run one container, behind HTTPS (e.g. Caddy on a small VPS), health check `/api/health`.
5. Back up the database nightly and keep the PII keys safe.

The repo's `docker-compose.yml` runs the same image locally (`docker compose --profile app up --build`).
